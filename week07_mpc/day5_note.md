# 什么是对账 为什么要对账
手头有的两份实现：
Python（W3）  fk_2link(t1, t2, L1, L2)  →  (x, y)
              用【几何法】直接写：x = L1·cos(θ1) + L2·cos(θ1+θ2)

C++（W7 Day 4）  arm::fk2link(t1, t2, L1, L2)  →  4×4 矩阵
              用【D-H 矩阵链】：dh(θ1,0,L1,0) * dh(θ2,0,L2,0)

两种不同的推导路径 一个是几何法三角函数 一个是矩阵连乘
对账就是喂同样的输入 看两边输出的数是否一样

光看代码逻辑和几组少量示例 都不可靠 必须至少：
50 组随机输入，误差 < 1e-9	证明两条推导路径在数值上等价

跨语言移植唯一可靠的验收方式：不是"看起来一样"，是"数一样"
而且这次对账特别有价值 —— 因为两边是同一个人、隔了三周、用了两种完全不同的方法做的
如果它们能对上，说明你对 FK 的理解是自洽的；如果对不上，必然有一边错了

# 简单介绍一下CSV和JSON  
简单说：CSV 是“Excel 表格”，JSON 是“带标签的字典”
例子：CSV如下：就是纯纯的表格
theta1,theta2,L1,L2,x,y
0.3,0.7,1.0,1.0,1.495,1.136
0.5,-0.2,2.0,0.5,2.18,1.01


例子：JSON如下；像一棵树或者嵌套的字典  适合表达复杂的关系  C++ 标准库完全不管 JSON。你必须引入第三方库
[
  {
    "theta1": 0.3,
    "theta2": 0.7,
    "lengths": { "L1": 1.0, "L2": 1.0 },
    "position": { "x": 1.495, "y": 1.136 }
  },
  {
    "theta1": 0.5,
    "theta2": -0.2,
    "lengths": { "L1": 2.0, "L2": 0.5 },
    "position": { "x": 2.18, "y": 1.01 }
  }
]

总结：简单平铺的数据用 CSV（省时省力）；复杂嵌套的数据（比如网络接口、配置文件）用 JSON（清晰易读）

用 JSON：要引 nlohmann/json，几百行头文件，编译时间翻倍
 用 CSV：20 行 std::ifstream + getline，零依赖

今天就用CSV，简单无引用依赖

# 写两个文件
day5_fk_crosscheck.py    生成用例
利用固定种子的随机数，生成 50 组极其刁钻的参数（关节角、连杆长度）
用几何公式算出这 50 组参数对应的“完美结果”（末端的 x, y 坐标）
把“题目”（输入的参数）和“标准答案”（算出来的 x, y），连同 17 位极限精度，打包写进 fk_cases.csv 表格里

day5_fk_crosscheck.cpp    读并比对
引入昨天刚打包好的 C++ 库（arm::fk2link），背后用的是复杂的齐次变换矩阵乘法。
任务：
打开 Python 发给它的那张卷子（fk_cases.csv）。
答卷：把 CSV 里前 4 列的数据（题目）喂给 fk2link 函数，算出一组新的 x, y 坐标。
阅卷：拿自己算出的 x, y，去减去 CSV 里后 2 列的数（标准答案），算误差。
打分：如果 50 组题的误差全部小于 10^−9，报告“对账通过”；只要有一组超了，立刻报警“对账失败”。

注意点：
%.17g 的生死存亡
如果你平时写代码，可能顺手就写 %.12f（保留 12 位小数）
惨案：如果你用 %.12f，存进 CSV 的时候，数字被截断了。C++ 读进去算的时候，理论上最大的误差只能达到 10^−12级别
为什么必须用 %.17g？
在 C++ 里，double 类型（双精度浮点数）最精准的有效数字就是 17 位。%g 是自动去掉末尾无用的零
用 %.17g，能保证 Python 写的数字，原汁原味、一位不差地被 C++ 读进来（这叫往返精度）
如果精度在这一步丢了，你后面的对账就变成了“比谁的截断误差大”，毫无意义

用了两种完全不同的数学流派（几何派 vs 矩阵派），用两种完全不同的语言（Python vs C++），如果在 50 组极其变态的随机数据下，它们居然能对出小数点后 16 位，这这说明你的理论推导、代码实现、精度处理，甚至库的链接，全部做到了无懈可击

# 关键一步 故意改错 
第一个：在 C++ 测试主程序里，把传给函数的 L1 和 L2 调换。

结果：误差瞬间飙到 2.619，50 组全炸。

为什么能抓住？ 因为之前测试用例里的 L1=2.0, L2=0.5 是不对称的。如果是对称的，你换位置也发现不了。

第二个：进入 kinematics.cpp 源码，在 dh(theta2, 0.0, L2, 0.0) 里，把 0.0 偷偷改成 0.001（d 参数偏移一毫米）。
结果：重新编译库后，误差变成了 10^−3级别，对账脚本再次报警！

为什么必须重新建库
你写的 day5_fk_crosscheck.cpp 并不去编译 kinematics.cpp，它链接的是一个已经编好的二进制包：

arm_control/src/kinematics.cpp
        │  g++ -c
        ▼
kinematics.cpp.o
        │  ar（打包成静态库）
        ▼
arm_control/build/libarm_control.a      ← 你会链接的就是这个"成品"
        ▲
        │  g++ 链接
day5_fk_crosscheck.cpp ─────────────► day5_fk_crosscheck（可执行文件）
改了 .cpp 却不重新 make，.a 里还是旧代码 —— 链接进去的也是旧代码

碰 CMake 项目，改完 src/ 里任何东西，第一反应必须是「库重建了吗」
